# GymTrack

GymTrack is a full stack weekly meal and workout planner. A FastAPI backend stores a seven day plan in a SQLite database and serves it through a JSON API. A browser interface, branded GymFuel, loads that plan and shows a lunch photo and a dinner photo for each day together with the workout schedule for that day.

## Features

- Seven day plan showing whether each day is a workout day or a rest day, the session time and the training focus
- Fourteen dishes with photos, with a lunch and a dinner assigned to every day
- Image viewer that opens a larger photo with the dish name; it opens with a click, Enter or Space and closes with Escape
- JSON API that returns the full plan in one request
- API key protected endpoints for changing the dishes assigned to a day and for renaming dishes
- Database tables created and filled with starting data automatically on first start
- Single command startup: the backend also serves the frontend, so no second server or build step is needed
- Interactive API documentation generated by FastAPI at `/docs`

## How It Works

1. The browser requests the home page. FastAPI serves `index.html`, `style.css`, `app.js` and the dish photos from the `frontend` folder.
2. When the page loads, `app.js` sends a `GET /api/plan` request to the backend.
3. The plan router reads the `days` and `dishes` tables through SQLAlchemy and returns the schedule, the meal plan and the dish names as JSON.
4. `app.js` builds one card per day from that data. Each card shows the workout details and the lunch and dinner photos, loaded from `/images/<dish number>.png`.
5. Clicking a photo opens the image viewer, which shows the meal type, the dish name and the day.
6. The admin endpoints change rows in the database. The next page load shows the updated plan.

On startup the application creates the database tables if they do not exist and, if the `dishes` table is empty, inserts the 14 dishes and the 7 days. The database is a single file, `backend/gymtrack.db`.

## Getting Started

### Prerequisites

- Git
- Python 3.13 (the pinned requirements were generated with this version)
- A web browser

No Node.js and no database server are needed.

### Clone the repository

```
git clone https://github.com/AlgoPhoenix369/gymtrack.git
cd gymtrack
```

### Create the virtual environment

Windows (PowerShell):

```
cd backend
python -m venv venv
venv\Scripts\Activate.ps1
```

If PowerShell blocks the activation script, run `Set-ExecutionPolicy -Scope Process -ExecutionPolicy Bypass` and activate again.

macOS and Linux:

```
cd backend
python3 -m venv venv
source venv/bin/activate
```

### Install dependencies

```
pip install -r requirements.txt
```

### Configure the environment

Copy the example file to `.env` inside the `backend` folder.

Windows (PowerShell):

```
Copy-Item .env.example .env
```

macOS and Linux:

```
cp .env.example .env
```

Open `.env` and set `ADMIN_API_KEY` to any value you choose. See [Configuration](#configuration) for details.

### Run the application

From the `backend` folder with the virtual environment active:

```
uvicorn app.main:app --reload
```

To make the application reachable from other machines, for example on a server:

```
uvicorn app.main:app --host 0.0.0.0 --port 8000
```

Open http://127.0.0.1:8000 in a browser. The API documentation is at http://127.0.0.1:8000/docs. To confirm the API is running:

```
curl http://127.0.0.1:8000/api/health
```

The response is `{"status":"ok"}`.

## Configuration

Settings are read from `backend/.env` when the server starts. Restart the server after changing them.

| Variable | Required | Description |
| --- | --- | --- |
| `ADMIN_API_KEY` | For admin endpoints | Secret that must be sent in the `X-API-Key` header on admin requests. If it is empty or missing, every admin request is rejected with 401. |
| `DATABASE_URL` | No | SQLite database URL. Defaults to a SQLite file at `backend/gymtrack.db`. |

The real `.env` file is excluded from Git. Only `.env.example`, which contains a safe placeholder, is committed.

## API Reference

All responses are JSON. Interactive documentation is available at `/docs`.

| Method | Path | Authentication | Description |
| --- | --- | --- | --- |
| GET | `/api/health` | None | Reports that the API is running |
| GET | `/api/plan` | None | Returns the schedule, the meal plan and the dish names |
| GET | `/api/dishes` | None | Returns all dishes |
| PUT | `/api/admin/days/{day_name}/meals` | `X-API-Key` | Changes the lunch or dinner dish for a day |
| PUT | `/api/admin/dishes/{dish_id}` | `X-API-Key` | Renames a dish |

### GET /api/plan

Returns three parts: `schedule` (workout details keyed by day name), `mealPlan` (the lunch and dinner dish numbers for each day) and `dishes` (dish names keyed by dish number). On a workout day, `time` holds the session time range and `focus` holds the training focus. The example is abbreviated:

```json
{
  "schedule": {
    "Saturday": { "isWorkout": false, "time": null, "focus": null }
  },
  "mealPlan": [
    { "day": "Monday", "lunch": 1, "dinner": 4 }
  ],
  "dishes": {
    "1": "Steamed mixed veggies, hard-boiled eggs, sliced avocado"
  }
}
```

### GET /api/dishes

```json
[
  { "id": 1, "name": "Steamed mixed veggies, hard-boiled eggs, sliced avocado" }
]
```

### PUT /api/admin/days/{day_name}/meals

The day name is not case sensitive. Both body fields are optional and fields that are left out are not changed.

Request body:

```json
{ "lunch_dish_id": 8, "dinner_dish_id": 4 }
```

Response:

```json
{ "day": "Monday", "lunch": 8, "dinner": 4 }
```


### Error responses

| Status | Meaning |
| --- | --- |
| 401 | The `X-API-Key` header is missing or incorrect |
| 404 | The day or dish does not exist |
| 422 | A referenced dish number does not exist, or the request body is invalid |

## Usage

### Viewing the plan

Open http://127.0.0.1:8000. Scroll through the seven day cards. Each card shows the day, whether it is a workout or rest day, the session time and focus for workout days, and the lunch and dinner photos. Click or press Enter on a photo to open it in the viewer. Press Escape or click outside the viewer to close it.

### Changing the plan through the API

Admin endpoints use the key set in `backend/.env`.

Windows PowerShell:

```
Invoke-RestMethod -Method Put -Uri http://127.0.0.1:8000/api/admin/dishes/2 -Headers @{"X-API-Key"="<your-admin-api-key>"} -ContentType "application/json" -Body '{"name":"Grilled chicken and rice"}'
```

macOS and Linux:

```
curl -X PUT http://127.0.0.1:8000/api/admin/dishes/2 -H "X-API-Key: <your-admin-api-key>" -H "Content-Type: application/json" -d '{"name":"Grilled chicken and rice"}'
```

Reload the page and open dish 2 to see the new name. The same requests can be sent from the `/docs` page by entering the key in the `x-api-key` field of an admin endpoint.

### Resetting the data

Stop the server, delete `backend/gymtrack.db` and start the server again. The tables are recreated and filled with the starting data.

## Design Decisions

- **SQLite.** The database is one file that needs no installation or configuration, which makes the project reproducible from a fresh clone.
- **One server for API and frontend.** FastAPI serves the frontend folder, so the whole application runs with one command, and the page and the API share an origin, so no cross-origin configuration is needed.
- **Response shape matches the frontend data.** `GET /api/plan` returns the same structure the original frontend kept in its source code, so the rendering code did not change when the data moved to the database.
- **Separated backend modules.** Configuration, database setup, models, schemas, authentication and routers each live in their own file.
- **Header based API key for admin routes.** The key comes from the environment, is compared in constant time and is never stored in the repository. Public routes need no key.
- **Seed on first start.** The starting data is inserted only when the database is empty, so restarting the server never overwrites changes.
- **Dish numbers tied to photo names.** Dish `n` uses `images/n.png`, so adding a dish means adding a row and a photo.
- **Pinned requirements.** `requirements.txt` lists exact versions so installs are repeatable.
- **Environment based secrets.** `.env` is ignored by Git and `.env.example` documents the variables.

## Troubleshooting

**Admin requests return 401.** Check that `backend/.env` contains the line `ADMIN_API_KEY=your-value`, including the variable name, and that the `X-API-Key` header uses the same value. Restart the server after editing the file.

**The page shows "Could not load the meal plan".** Open the site through the backend address, http://127.0.0.1:8000, and not by opening `index.html` as a file. Confirm the server is running and that http://127.0.0.1:8000/api/health responds.

**ModuleNotFoundError: No module named 'app'.** Run the `uvicorn` command from the `backend` folder, not from the repository root.

**Port 8000 is already in use.** Start the server on another port, for example `uvicorn app.main:app --port 8001`, and open that port in the browser.

**PowerShell blocks the activation script.** Run `Set-ExecutionPolicy -Scope Process -ExecutionPolicy Bypass` and activate again. The change applies only to the current window.

**A dish shows a placeholder instead of a photo.** Confirm that `frontend/images/<dish number>.png` exists. The page shows a labelled placeholder when a photo cannot be loaded.

**Dependency installation fails.** Confirm that the active Python version is 3.13 with `python --version`, and that the virtual environment is active.
